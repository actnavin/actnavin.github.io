Upgrading a Legacy Rails App in a Compliance-Sensitive Domain

By Navin Kumar · Software Engineer, Ruby on Rails · Mar 2019 – Aug 2019

Moving an insurance and healthcare client's Ruby on Rails application onto a current, supported release — without breaking what was already in production.

Short version: a client in the insurance and healthcare space was running a Ruby on Rails application on an older major version. I upgraded it to a current, supported release, modernised background job processing with Sidekiq along the way, and worked directly with client stakeholders to keep the migration low-risk in a domain where mistakes are expensive.

The context

Legacy Rails upgrades carry a specific kind of risk in insurance and healthcare: the application usually touches sensitive data and business-critical workflows, so "just bump the version and fix what breaks" isn't an acceptable plan. The client needed to get off an older, increasingly unsupported Rails release without disrupting the systems built on top of it.

What I did

I planned and executed the upgrade to a current, supported Rails release — working through the deprecations, dependency bumps, and behavioural changes that come with moving a real, running application forward rather than starting fresh. As part of the same engagement, I modernised the application's background job processing using Sidekiq, replacing older job-handling patterns with something more reliable to operate and easier to reason about.

Because this was a compliance-sensitive domain, the technical work wasn't the only constraint. I worked directly with client stakeholders to scope the upgrade, sequence it into safe stages, and de-risk it — flagging what needed manual verification rather than assuming automated test coverage caught everything a healthcare or insurance workflow depends on.

Why this is harder than a greenfield build

Upgrading a legacy application means every decision is constrained by what's already there. You inherit someone else's data model, someone else's conventions, and — in a regulated-adjacent domain — someone else's tolerance for risk. The job is as much about judgment on what not to touch as it is about writing the upgrade code itself.

Why this matters if you're hiring: a lot of Rails developers can write new features. Fewer have sat with a legacy, business-critical application and made the call on what's safe to change, in what order, without a client's operations grinding to a halt.

Sitting on a Rails app that's a version or two (or five) behind? Let's talk about what a safe upgrade path looks like.
