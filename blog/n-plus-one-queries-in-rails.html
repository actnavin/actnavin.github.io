How to Find and Fix N+1 Queries in Rails

By Navin Kumar · Freelance Ruby on Rails Developer & Engineering Leader · Updated 13 Aug 2026 · 7 min read

The most common performance bug in Rails apps, why includes alone doesn't always fix it, and how to actually verify you've eliminated it rather than just hoping.

Short answer: an N+1 query happens when loading N records triggers one extra query per record instead of one query total. Fix it by eager loading the association with includes, preload, or eager_load — but always confirm the fix with an actual query count, since eager loading code that doesn't match how the association is really accessed silently does nothing.

What an N+1 query actually is

Say you're rendering a list of blog posts with their author's name:

posts = Post.limit(20)

posts.each do |post|
  puts post.author.name
end

This runs 21 queries: one to load the 20 posts, then one more per post to load that post's author, because post.author triggers a fresh query the first time it's accessed on each individual post object. Twenty posts today, two hundred next quarter — the query count scales linearly with the data, which is exactly why this bug is invisible in development with a handful of seed records and painful in production.

How to actually find them

Don't rely on eyeballing the code — N+1s hide in scopes, serializers, and view partials just as often as in obvious loops. Three ways to catch them for real:

  • The bullet gem — runs in development, watches your actual queries, and warns (in the browser, the log, or as an alert) exactly where an N+1 happened and which association triggered it. This is the single highest-value tool for this problem; if you don't have it installed, that's the first thing to add.
  • rack-mini-profiler — shows a live query count and timing breakdown as a small overlay on every page while you develop, so you notice a page jump from 5 queries to 45 queries the moment you introduce the regression.
  • Query-count assertions in tests — wrap a suspect action in assert_queries_count (Rails 7.1+) or the older ActiveRecord::QueryRecorder pattern, and fail the test if the count exceeds a fixed number. This is the only approach that actually prevents a fixed N+1 from silently coming back in a later refactor.

The fix: includes, preload, and eager_load

All three tell Rails to load an association up front instead of lazily, but they're not interchangeable in how they do it:

Rails eager-loading strategies
MethodStrategyQuery count
preloadAlways a separate query per association2 queries (posts, then authors)
eager_loadAlways a single query via LEFT OUTER JOIN1 query
includesPicks preload by default, switches to eager_load automatically if you reference the association in where/order1 or 2, depending

The fix for the example above:

posts = Post.includes(:author).limit(20)

posts.each do |post|
  puts post.author.name  # no extra query — already loaded
end

For most cases, includes is the right default — let Rails choose the strategy. Reach for preload explicitly when you want to guarantee separate queries (useful for very wide joins that would otherwise return a huge duplicated result set), and eager_load explicitly when you need to filter or sort by a column on the associated table:

# Needs eager_load (or includes, which will pick it automatically here)
# because the WHERE clause touches the authors table directly.
Post.eager_load(:author).where(authors: { verified: true })

Why includes sometimes doesn't work

This is the part that trips people up: adding includes and assuming the problem is solved, without checking. A few ways it silently fails:

  • Calling a scope instead of the loaded association — post.author reads the preloaded record, but post.author.posts.published or any chained scope on the association re-queries, because a scope is a new relation, not the object already in memory.
  • Conditional associations built at query time — if the association itself is defined with a runtime condition that can't be captured by a simple preload, Rails may fall back to querying per record anyway.
  • Serializers that don't know what was preloaded — in a JSON API, if the controller eager loads correctly but the serializer independently calls a different, un-preloaded association for each record, you've just moved the N+1 one layer deeper. This is the single most common place I've found N+1s hiding in production Rails APIs — the controller looks correct in isolation, and the bug only shows up in the serializer layer.

Rule of thumb: after adding eager loading, don't just eyeball it — check the actual query count (bullet, rack-mini-profiler, or a test assertion). "I added includes" is not the same claim as "I verified this page makes a fixed number of queries regardless of how many records it returns."

When eager loading isn't enough

A few situations where includes/preload/eager_load alone won't get you there:

  • You only need a count, not the records — use a counter_cache column instead of loading and counting an association's records.
  • The association is polymorphic across many types — eager loading still works, but batch-load carefully; a naive preload across a large polymorphic association can pull in far more than you need.
  • You're aggregating across a huge dataset — at that scale, a single SQL aggregate query (or a materialized view) usually beats loading records into Ruby at all, N+1 or not.

FAQ

Does includes always fix an N+1 query in Rails?

Only if the association is actually accessed the way Rails expects. If your code calls a scope or method that re-queries instead of reading the preloaded records, you can still get an N+1 with includes in place. Verify with a query count, not just by adding includes.

What is the difference between includes, preload, and eager_load?

preload always runs a separate query per association. eager_load always uses a single query with a LEFT OUTER JOIN. includes picks one of the two automatically based on whether you reference the association in a where or order clause.

Can N+1 queries happen in a JSON API with a serializer?

Yes — it's one of the most common places they hide. If a serializer calls an association method per record and the controller didn't eager load that specific association, you get one query per record regardless of how clean the controller code looks.
